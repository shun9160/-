# トレーダータイプ診断 仕様書

MyFX BOOK の「トレーダータイプ診断」の仕様と実装のまとめ。

この診断は **MBTI のコピーではなく、人格を断定するものでもない**。
アンケートの回答と、このアプリに記録された取引から、
**いまのトレードの傾向**を6タイプで整理して見せる機能。
取引データが変われば結果も変わる、という前提で作ってある。

---

## 1. 前提・未確定事項

実装前に既存リポジトリを確認した結果は次の通り。

| 項目 | 実際 |
| --- | --- |
| フレームワーク | React 18 + TypeScript + Vite 5 |
| スタイル | Tailwind CSS 3（`tailwind.config.js` のトークンを使う） |
| DB / 認証 | Supabase（Postgres + Auth）。RLS は `auth.uid() = user_id` |
| API | アプリサーバーは無く、画面から PostgREST を直接叩く方式。<br>外部からの受け口だけ Netlify Functions（`netlify/functions/ingest.mts`）にある |
| テスト環境 | **無かった** → 本機能で vitest を追加 |
| アニメーションライブラリ | **無かった** → 追加していない（後述） |
| 既存の診断・キャラクター表示 | **無かった** → 新規 |
| 取引データ構造 | `src/lib/types.ts` の `Trade` / `EnrichedTrade` |

### 置いた仮定

1. **Rive / Lottie は入れなかった。**
   キャラクターの絵そのものがまだ無いため、いま入れても動かすものが無い。
   仕様書の許容（「実体がまだない場合は assetKey を利用したプレースホルダー構造に」）に従い、
   差し替え可能な構造だけ用意した。差し替え方法は §10。

2. **このアプリに無いデータ項目は、0点にせず「判定しない」。**
   仕様書のデータ指標のうち、戦略タグ／セットアップタグ／モメンタム系タグ／
   エントリー機会の実行率／事前チェックリストは、いまのデータモデルに存在しない。
   これらは `score = null` として **ウェイトから外し、残りで割り直す**（§5）。

3. **「1取引あたりのリスク率」は `|建値 − 損切り| × ロット × 1ロットの通貨量 ÷ 原資` で近似した。**
   口座の原資が未設定（0）のときは、資金比率を使う指標も「判定しない」に落ちる。

4. **「複数戦略で利益を出せている割合」は「複数の銘柄で利益を出せている割合」で代用した。**
   戦略タグが無いため。3件以上ある銘柄が2種類以上そろって初めて判定する。

5. **診断の入口は「分析」タブの中の「タイプ診断」**にした。
   モバイルの下部タブは5つで埋まっており、6つ目を足すと窮屈になるため。

## 2. 6タイプ

優劣は付けない。どのタイプにも強みと注意点の両方を必ず持たせている。
定義は `src/lib/diagnosis/types.ts` の `TYPES` に一元管理（タイプ追加はここに足すだけ）。

| ID | 日本語 | 分類 | 色 | コピー |
| --- | --- | --- | --- | --- |
| BLAZE | ブレイズ | 突破型トレーダー | `#E1620E` | 流れが来たら、迷わず乗る。 |
| LOGIC | ロジック | 分析型トレーダー | `#1D4ED8` | 答えは、記録の中にある。 |
| GUARD | ガード | 防衛型トレーダー | `#15803D` | 守れる人だけが、最後まで残る。 |
| SHIFT | シフト | 適応型トレーダー | `#BE185D` | 相場が変われば、自分も変える。 |
| WATCH | ウォッチ | 観察型トレーダー | `#7C3AED` | 待つことも、戦略のひとつ。 |
| RISE | ライズ | 再起型トレーダー | `#B45309` | 負けた後の行動が、未来を決める。 |

## 3. 診断方式とステータス

アンケートと取引データを、記録された取引件数に応じて配分する。
（`src/lib/diagnosis/config.ts` の `STATUS_RULES`）

| 取引件数 | ステータス | アンケート | 取引データ |
| --- | --- | --- | --- |
| 5件未満 | `questionnaire_only` | 100% | 0% |
| 5〜19件 | `provisional` | 65% | 35% |
| 20件以上 | `data_backed` | 35% | 65% |

---

## 4. アンケート

- 24問（`src/lib/diagnosis/questions.ts`）。各タイプに4問ずつ、うち1問が逆転質問。
- 5段階（1: まったく当てはまらない 〜 5: 非常に当てはまる）。
- 直接採点 `((answer - 1) / 4) * 100` / 逆転採点 `((5 - answer) / 4) * 100`。
- タイプのアンケートスコア＝その4問の平均。未回答のタイプは **0点ではなく中立の50点**。
- 画面には1ページ4問ずつ出す。
- **どの質問がどのタイプに効くかは画面に渡さない。**
  `/questions` が返すのは `{ id, text }` だけ（テストで検証済み）。

---

## 5. 取引データスコア

`src/lib/diagnosis/behavior.ts`。ウェイトは `config.ts` の `BEHAVIOR_WEIGHTS`。

| タイプ | 指標（ウェイト） | このアプリで取れるか |
| --- | --- | --- |
| BLAZE | 1日あたり取引数 30% / 保有時間の短さ 20% / 平均計画RR 20% / モメンタム系タグ比率 20% / 実行率 10% | 前3つのみ（合計70%） |
| LOGIC | SL・TP事前設定率 25% / 記録の記入率 25% / リスクの一貫性 25% / セットアップタグの一貫性 25% | 前3つのみ（75%） |
| GUARD | 損切り設定率 25% / 平均リスク率の低さ 25% / 最大DDの低さ 25% / 実損失が計画内の割合 25% | 全部（原資未設定なら50%） |
| SHIFT | 戦略の分散度 30% / 時間帯の分散度 20% / 銘柄の分散度 20% / 複数の場面で利益 30% | 後3つのみ（70%） |
| WATCH | 取引数の少なさ 20% / 勝率 20% / SL・TP事前設定率 20% / 損切り直後の入り直しの少なさ 20% / 事前計画の記入率 20% | 前4つのみ（80%） |
| RISE | リカバリーファクター 25% / 損失後のルール遵守率 25% / 負け取引の記録率 25% / 直近の改善傾向 25% | 全部 |

### 欠損データの扱い（重要）

- **欠けた指標は0点にしない。** `score = null` にしてウェイトから外し、
  残りのウェイトで割り直す（`combineIndicators`）。
- **取れたウェイトの合計が50%未満のタイプは、取引データスコアを使わない**（`null`）。
  そのタイプはアンケートスコアだけで判断される。
- 標本が3件に満たない指標（平均保有時間、勝率など）も判定しない。

### 共通ヘルパー（`src/lib/diagnosis/scoring.ts`）

| 関数 | 内容 |
| --- | --- |
| `scale(v, low, high)` | low以下→0、high以上→100、あいだは線形。`low > high` なら逆向き |
| `inverseScale(v, low, high)` | `100 - scale(...)` |
| `ratioScore(v)` | 0〜1を0〜100に。範囲外はクランプ |
| `normalizedEntropy(counts)` | 分散度。1種類なら0、均等なほど100 |
| `consistencyScore(values)` | 変動係数。ばらつきが小さいほど高得点。ゼロ平均は `null` |

## 6. 総合スコアと表示の出し分け

```
finalScore = questionnaireScore × questionnaireWeight
           + behaviorScore     × behaviorWeight     （0〜100にクランプ）
```

取引データスコアが `null` のタイプは、アンケートスコアをそのまま使う。

1位と2位の差による見せ方（`DISPLAY_GAP`）:

| 差 | 表示 |
| --- | --- |
| 8点以上 | 1位だけを強く出す（`single`） |
| 3〜8点未満 | 1位＋「サブ傾向」（`with_secondary`） |
| 3点未満 | ハイブリッド表示（`hybrid`）。ただし1位は必ず決める |

### 同点のとき

タイプIDの並び順では決めない。次の順で解く。

1. 取引データスコアが高い方
2. アンケート内の回答一貫性が高い方
3. 直近30日の取引だけで採点し直して、より合っている方
4. それでも決まらなければ **追加の1問**を画面に出す（`needsTiebreak: true`）

## 7. 信頼度

0〜100。内訳は `CONFIDENCE_WEIGHTS`。

回答済み質問数 20% / 回答の一貫性 15% / 取引数 20% / 取引期間 10% /
必要データの充足率 15% / 1位2位の差 10% / 直近データの新しさ 10%

| 値 | 言い換え |
| --- | --- |
| 0〜39 | 参考結果 |
| 40〜69 | 暫定タイプ |
| 70〜84 | 信頼度の高い結果 |
| 85〜100 | 取引データに基づく明確な傾向 |

## 8. API

Netlify Function `netlify/functions/trader-diagnosis.mts`（`/api/trader-diagnosis/*`）。
中身は `src/lib/diagnosis/api.ts`（DBアクセスと時計を注入する形なのでテスト可能）。

| メソッド | パス | 内容 |
| --- | --- | --- |
| GET | `/api/trader-diagnosis/questions` | 質問一覧（タイプとの対応は含まない） |
| POST | `/api/trader-diagnosis/calculate` | 回答を送って採点。結果を1行追加 |
| POST | `/api/trader-diagnosis/recalculate` | 前回の回答のまま、いまの取引記録で採点し直す |
| GET | `/api/trader-diagnosis/latest` | 最新の結果＋再診断のおすすめ |
| GET | `/api/trader-diagnosis/history` | 履歴（最大20件） |
| GET | `/api/trader-diagnosis/:id` | 1件 |
| POST | `/api/trader-diagnosis/:id/actions/:actionId/complete` | 改善アクションの完了・取り消し |

仕様書の候補にあった `POST /answers` は用意していない。
回答は `calculate` と同時に保存され、下書きだけを別に持つ必要が無かったため。

### 守っていること

- **クライアントからスコアは受け取らない。** 受け取るのは1〜5の回答だけで、
  それ以外の値（`scores` など）は `sanitizeAnswers` が捨てる。
- **採点は必ずサーバー側**（Function 内）で行う。
- 本人確認は Supabase のアクセストークン。無効なら 401、他人のIDを指定すれば 404。

必要な環境変数（Netlify のサイト設定）:

```
SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY   ← 絶対に画面に出さない
SUPABASE_ANON_KEY           ← 省略可（トークン確認に使う）
```

## 9. データベース

`supabase/migrations/2026-08-06_trader_diagnosis.sql`（Supabase → SQL Editor に貼って Run）。

### `trader_diagnoses`

診断の履歴。**過去の結果は書き換えない。** 毎回あたらしい行として積む。
UPDATE はトリガーでDB側から止めてある。
RLS は「自分の行を読むだけ」。書き込みは service_role（＝サーバー側）だけができる。

主な列: `diagnosis_version` / `question_version` / `scoring_version` /
`status` / `primary_type` / `secondary_type` / `confidence` / `trade_count` /
`scores` / `result`(結果まるごと) / `answers`

### `trader_diagnosis_actions`

改善アクションの完了だけを別表にした。
これがあるおかげで、診断の行そのものは一切書き換わらない。

## 10. キャラクター

各タイプに `happy` / `sad` / `cheer` の3状態。状態は取引記録から決める（`pickCharacterState`）。

- `sad`: 3連敗以上、または直近が負けかつ資金の落ち込みが大きい
- `happy`: 直近がプラスで、損切りを置けている or 改善傾向がある
- それ以外: `cheer`（診断直後の既定）

**`sad` でもユーザーを責めない。** 文言は `messages.ts` の `CHARACTER_MESSAGES` に集約。

### 絵の差し替え方

いまは絵が無いので、`src/components/diagnosis/CharacterFigure.tsx` が
タイプ色の代用図（表情つき）を描いている。

1. 画像を置く

```
public/characters/
  blaze/  happy.webp  sad.webp  cheer.webp
  logic/  ...
  guard/  ...
  shift/  ...
  watch/  ...
  rise/   ...
```

（ディレクトリ名は `TYPES[id].characterId`。`assetKey` は `characters/<id>/<state>` を返す）

2. `CharacterFigure.tsx` の `HAS_ASSETS` を `true` にする

これだけで差し替わる。読み込みに失敗したら自動で代用図に戻る。

Rive を使う場合も、同じ場所に `.riv` を置き、この1ファイルだけ差し替えればよい
（`@rive-app/react-canvas` の追加が必要になるので、絵ができてから入れる）。
Rive が合わなければ Lottie → アニメーションWebP → 静止WebP の順で落とす。

## 11. バージョン管理

`config.ts` に3つ持ち、結果の行にも保存する。

```
DIAGNOSIS_VERSION = '1.0.0'
QUESTION_VERSION  = '1.0.0'
SCORING_VERSION   = '1.0.0'
```

質問・ウェイト・閾値を変えたら **必ず上げる**。
過去の行には当時の版と結果まるごとが残っているので、後から読み解ける。

## 12. 安全性と表現

この診断は **投資助言ではない**。次の表現は使わない。

- 利益を保証する表現
- 特定の売買を直接すすめる表現
- 「このタイプなら必ず勝てる」
- 人格や能力を断定する表現
- 損失をユーザーの性格だけに帰属させる表現
- 過度に不安を煽る表現
- 損失時にキャラクターがユーザーを責める表現

改善アクション（`ACTION_TEMPLATES`）は、**売買のしかたではなく記録のしかた**だけを扱う。
タイプ間に優劣・ランキングは付けない。結果画面には毎回この注意書きを出す。
